## Non-obvious things worth knowing before you touch this again

- **WordPress's default "Hello world!" sample post (ID 1) was never
  deleted after install, and it broke `/news/`'s "Latest" featured
  slot.** Found from a screenshot Oren sent showing a real, visually
  blank grey box at the top of `/news/` — every earlier automated check
  this session had only verified the archive grid and single-post pages,
  never this specific featured/"Latest" hero block in `home.php`, so it
  went unnoticed through several rounds of "confirmed working" checks.
  Because the sample post was dated at install time, it sorted as the
  newest post ahead of all 42 real migrated News entries, and since it's
  not real content it has no featured image — hence the blank box.
  Deleted the post (and its one default comment), cleared both cache
  layers, confirmed the real "MDW's Final Weekend" post now shows
  correctly in that slot. **If a fresh install of this theme/plugin pair
  ever happens again, delete the default "Hello world!" post as one of
  the very first steps** — it's not currently in any seeder or
  `docs/INSTALL.md` checklist, and it silently corrupts the "Latest"
  logic on any home.php-style featured-post pattern, not just this one.
- **The tar-deploy phantom-directory bug bit again this session, briefly.**
  Deploying the footer fix, a `tar czf - themes/ilanel-poc` was run from
  the repo root and piped into the server's `themes/` directory instead
  of `cd`-ing into `themes/` first — this created
  `themes/themes/ilanel-poc` and left the live site's actual theme
  directory **empty** for a few minutes. Site stayed up (served from
  Breeze's cache the whole time), recovered by moving the misplaced
  folder back into place, confirmed via `wp theme status` and `php -l`
  after. **Always `cd` into the theme's own immediate parent before
  `tar czf -`, never the repo root** — this is now the second time this
  exact mistake has happened on this project (see
  `HANDOVER-2026-08-14.md` for the first).
- **`has_post_thumbnail()` checks over SSH are shell-quoting-fragile.**
  Spent real time this session chasing a reported "News hero image is
  blank" bug that turned out to be entirely a shell double-quoting
  mistake in a diagnostic loop (`$id` interpolating wrong inside nested
  SSH+bash quoting), not a real site issue — every post actually has a
  working thumbnail, verified multiple ways once the script was fixed.
  If a similar report comes in again: write the check to a `.sh` file
  and `bash` it remotely rather than inlining loops into an SSH command
  string, it's much less error-prone.
- **Codex CLI's web/browser access is currently broken in this
  environment, not just unreliable.** Tried delegating a live-site UX
  audit to it — it has no real browser automation (no Playwright/
  Puppeteer/DevTools MCP), only a fetch-and-read tool, and that fetch
  tool rejected all 6 test URLs outright ("unsafe/non-retryable"), then
  its own sandboxed PowerShell fallback was blocked by network
  permissions too. Codex CLI's shell/file-editing work (writing
  `scripts/configure-commerce.php`, for instance) worked perfectly fine
  the same session — the failure is specific to its web-fetch path, not
  Codex generally. Don't delegate live-site verification to it until this
  changes; do delegate local file/script work, that's solid.
- **Object-cache-pro (Redis) is active** alongside Breeze's page cache —
  two separate cache layers to consider when something looks "stale" or
  "missing" right after a change. `wp cache flush` clears the Redis
  object cache; `wp breeze purge --cache=all` clears Breeze's page cache.
  Both may need clearing after a database-level change (an `wp option
  update`, a seeder re-run) before it's visible on the live site.
- **The Cloudways master SFTP password rotation is still open** — flagged
  in `HANDOVER-2026-08-14.md`, routed to Oren directly since it's
  dashboard-only, not something doable over SSH. Not confirmed done as of
  this handover; ask before assuming it happened.
