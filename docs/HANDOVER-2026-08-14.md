## Non-obvious things worth knowing before you touch this again

- **WooCommerce ships a "Coming Soon" store mode** on fresh installs that
  silently swaps every product page for a placeholder — looks exactly like
  a caching bug (cleared three cache layers before finding it). Already
  fixed on this install (`woocommerce_coming_soon` / `_store_pages_only`
  both `no`), but if you ever spin up a fresh Cloudways instance again,
  check this first.
- **`show_on_front` matters for any custom archive route.** `/news/` was
  resolving to the homepage template until `show_on_front` was set to
  `page` with a real static front page — WordPress's `is_front_page()` is
  true for any "posts" query when this is left at its default, which
  swallows custom rewrite rules that also resolve to a bare post query.
  Already fixed; documented in `docs/INSTALL.md` §Configuration since it's
  not something either seeder sets.
- **The WP-CLI seeder and the Playground blueprint generator
  (`build-playground-blueprint.js`) have drifted at least three separate
  times this session** — product image sideloading, Light Art seeding, and
  finish-swatch matching were all present in the Playground path but
  missing from the real WP-CLI seeder. If something works in the
  Playground demo but not on the real Cloudways install, check this file
  pair first before assuming a new bug.
- **Codex CLI's web-fetch tool is unreliable in this environment** — failed
  repeatedly with "cache miss" errors and backend disconnects on anything
  beyond ~4-5 URLs in one run, while plain `curl` from this shell worked
  every time. If delegating live-site verification to Codex, keep batches
  small or just do it directly.
- **The Cloudways master SFTP password was pasted in plaintext in this
  session's chat at one point** — worth rotating from the Cloudways
  dashboard if that hasn't happened yet. SSH key auth (the one referenced
  above) doesn't depend on it.
